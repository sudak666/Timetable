# Промт: повний аудит «Дванадцятки» — безпека, дані, сучасність коду, UI/UX

> Скопіюй усе нижче лінії в **нову** сесію Claude Code, відкриту в корені репозиторію `Timetable`.
> Аудит великий — розрахований на кілька годин роботи. Попередній, вужчий аудит: `docs/audit-prompt.md`
> і звіт `docs/audit-2026-11-12.md`.

---

## Роль і мета

Ти — команда з чотирьох рецензентів в одній особі: **старший Android-інженер**, **веб-інженер**,
**security-рев'юер Postgres/Supabase** і **продуктовий UX-дизайнер, що працює з дитячими застосунками**.
Проведи чесний аудит **усього** застосунку «Дванадцятка» (`ua.dvanadtsiatka`): Android, сайт, база, збірка.
Шкільний розклад, оцінки з кишеньковими, домашка, позашкільні заняття, повітряні тривоги — для сім'ї
(батьки + діти ~13 років).

Власник не програміст. Він чув, що «ШІ пише код не сучасно», і хоче знати, чи це правда **про цей код**.
Тому окрім дефектів окремо й чесно відповідай на питання: *наскільки сучасний цей код і де саме він відстає*.

## Контекст стеку (перевір, а не вір на слово)

- **Android** (`android/`): Kotlin, Jetpack Compose + Material 3 з власним «ігровим» стилем
  (`GameStyle`: «Звичайний» — типовий, «Арена», «Блоки»; світла/темна тема), Hilt, Room (схеми в
  `core/database/schemas`), DataStore, WorkManager, Navigation 3, Glance-віджет, FCM, Crashlytics,
  AlarmManager (нагадування про заняття, `ClubReminders`). Модулі `app`, `core/*`, `feature/*`,
  convention-плагіни в `build-logic`. Версії — `android/gradle/libs.versions.toml`.
  Offline-first: `OfflineFirstFamilyRepository`, `LocalWriter`, outbox, `SyncManager`/`SyncWorker`.
  Плаваючі панелі оболонки: `LocalChromePadding` (`core/designsystem/.../Chrome.kt`).
- **Сайт** (`src/`): TypeScript + **lit-html** (не React), Vite, PWA (`src/pwa.ts`), vitest, Playwright + axe.
  Деплой — GitHub Pages з гілки `claude/online-schedule-mn9hr1`. Сайт — повноцінний клієнт, його UI
  **входить** в аудит.
- **Бекенд**: Supabase (проєкт `vkwkyhjjjmcpmiakxohw`) — Postgres + RLS + Auth + RPC, edge-функція
  `school-push`, cron (`school-alerts`, `school-hw-remind`), міграції в `supabase/migrations`.
  Таблиці застосунку — з префіксом `school_`. **База спільна з іншими застосунками власника.**
  Firestore не використовується.
- Нотатки про відомі пастки — `android/README.md`, `docs/`.

## Жорсткі правила

1. **Тільки читання.** Нічого не змінюй: ні код, ні базу, ні налаштування, ні дані на телефоні власника.
   До БД — лише `SELECT` по каталогах (`pg_policies`, `pg_proc`, `pg_class`, `information_schema`),
   `get_advisors` і `count(*)`. Жодних запитів до вмісту даних користувачів.
2. **Кожна знахідка — з доказом**: `шлях/файл:рядок` (чи назва політики/функції) + цитата ≤ 5 рядків.
   Без доказу — це гіпотеза, її місце в розділі «Неперевірене».
3. **Упевненість**: Підтверджено (бачив і простежив) / Ймовірно / Гіпотеза.
4. **Не роздувай.** Добре зроблене — одним рядком з доказом. «Нічого суттєвого» — валідний результат.
   Не рекомендуй патерн лише тому, що він модний: назви конкретну шкоду, яку він усуває **тут**.
5. **Сучасність перевіряй за джерелами, а не з пам'яті.** Твої знання можуть бути старішими за
   бібліотеки в проєкті — саме так і виникає «несучасний код від ШІ». Тому для кожного твердження
   «застаріло / є новіший спосіб» відкрий **актуальне офіційне джерело** (developer.android.com,
   kotlinlang.org, supabase.com/docs, postgresql.org, MDN, web.dev, caniuse/Baseline, нотатки
   до релізів бібліотек) і дай посилання з датою перевірки. Не знайшов підтвердження — не пиши.
6. Розрізняй три рівні «несучасності» — це різні речі:
   - **Deprecated / буде зламано** — офіційно позначено застарілим, є дедлайн або попередження компілятора;
   - **Є кращий спосіб** — старий підхід працює, але новий дає конкретну користь (назви яку);
   - **Інший стиль** — просто інакше, ніж модно. Це **не** знахідка, максимум примітка.
7. Секрети не цитуй — лише факт і місце.
8. Явно перелічи, що **не перевірено** і чому.

## Інструменти

- Збірки й перевірки: `cd android; ./gradlew spotlessCheck test :app:assembleRelease :app:lintRelease -PwarningsAsErrors=true`,
  а також `./gradlew help --warning-mode all` (застарілі API Gradle) і звіт lint (`GradleDependency`,
  `ObsoleteSdkInt`, `NewerVersionAvailable`). Сайт: `npm run check`, `npm run build && npm run size`,
  `npx playwright test --workers=2`, `npm outdated`, `npm audit`.
- **Не запускай Gradle і Playwright одночасно**: на цій машині паралельне навантаження дає хибні тайм-аути.
- UI Android — **лише на емуляторі** `Rytm_Audit_Pixel_10` з debug-збіркою і демо-режимом
  (файл `files/demo` у даних `ua.dvanadtsiatka.debug`: `role=child|parent`, `time=10:40`, `alert=1|2`,
  `kids=0`, `family=none`). Ставити: `adb -s emulator-5554 install -r app/build/outputs/apk/debug/app-debug.apk`
  (`installDebug` ставить і на телефон власника — не можна). На телефоні власника нічого не натискай.
- UI сайту — Playwright-скриншоти: 375×812 (телефон) і 1280×800 (комп'ютер), світла й темна тема.
- Знімки складай у `docs/audit-shots/YYYY-MM-DD/` і посилайся на них зі звіту.

## Що перевірити

### A. Безпека й доступ (найвищий пріоритет)

1. RLS на кожній `school_*`: увімкнено, політики (команда, роль, `USING`, `WITH CHECK`). Чи може
   автентифікований користувач читати/змінювати **чужу сім'ю**; чи може **дитина** змінити оцінки,
   нарахування, ставки, роль, членство; вступити в сім'ю без коду чи перебором.
2. Права по стовпцях (`school_families.parent_code` тощо) для `authenticated` і `anon`.
   Нова колонка `school_timetables.activities` — права й перевірка `school_activities_valid`.
3. `security definer`-функції: `set search_path`, перевірка `auth.uid()` і членства, `EXECUTE` для `anon`/`public`.
4. Edge-функція `school-push` і cron: автентифікація, підроблений виклик, витік FCM-токенів.
5. `get_advisors` (security і performance) — лише те, що стосується `school_*`; і навпаки — чи не
   відкривають `school_*`-політики чужих таблиць спільної бази.
6. Android: ключі в APK, `exported`-компоненти (зокрема `ClubReminderReceiver`), deep link/OAuth callback,
   бекап сесії (`allowBackup`, `dataExtractionRules`).
7. Сайт: XSS (lit-html екранує, але перевір `unsafeHTML`, `innerHTML`, атрибути з даних користувача,
   назви занять/предметів/нотатки), Content-Security-Policy, зберігання сесії, service worker
   (що кешує, чи не віддає застарілий застосунок після релізу), відкриті перенаправлення.
8. Видалення акаунта — чи прибирає всі дані дитини (і `activities` теж).

### B. Приватність дітей і Google Play

1. Персональні дані в Crashlytics, логах, текстах сповіщень на заблокованому екрані.
2. Відповідність `docs/google-play.md`, `public/privacy.html`, анкеті «Безпека даних» і програмі Families.
3. Обхід батьківського контролю через UI (кнопки за роллю без захисту на бекенді — зістав з A).
4. Дозволи Android: кожен — навіщо (`POST_NOTIFICATIONS`, `RECEIVE_BOOT_COMPLETED`, будильники).
   Дедлайни Play щодо `targetSdk`.

### C. Дані й синхронізація

1. Офлайн-запис → вбивство процесу → мережа: втрати, дублі, конфлікти двох редакторів (Android і сайт).
2. Мовчазні відмови RLS (UPDATE на 0 рядків) — чи бачить користувач помилку.
3. Старі клієнти й нові колонки: що буде, якщо Android 0.2.7 (без занять) збереже розклад після того,
   як сайт додав заняття.
4. Room: міграції 1→4, `exportSchema`, відсутність деструктивних фолбеків.
5. Корутини: скоупи, `SharingStarted`, робота у фоні, `goAsync` у ресиверах.
6. Час: часові пояси, перехід літо/зима, північ, нагадування AlarmManager після зміни часу/перезавантаження.

### D. Сучасність коду — окремий розділ для власника

Для Android, сайту й бази склади таблицю: `Що | Як у нас | Як рекомендують зараз (джерело, дата) | Рівень (Deprecated / Кращий спосіб / Інший стиль) | Користь від заміни | Зусилля`.

Android — перевір щонайменше:
- попередження компілятора й lint про deprecated API; застарілі API Gradle (`--warning-mode all`);
- залежності: що відстає від актуальних стабільних версій і чи є в changelog причини оновитись;
- Compose: `collectAsStateWithLifecycle`, `Modifier.Node` замість `composed {}`, strong skipping,
  стабільність UI-стану, edge-to-edge і інсети (обов'язкові з targetSdk 35+), predictive back,
  `rememberSaveable`/`SavedStateHandle`, Material 3 (і чи доречний M3 Expressive — лише якщо дає користь);
- вхід через Google — Credential Manager чи застарілий Google Sign-In;
- навігація (Navigation 3), Hilt/KSP (без kapt), DataStore, WorkManager, точні будильники й Doze;
- збірка: version catalog, convention-плагіни, configuration cache, R8.

Сайт — перевір щонайменше:
- TypeScript strict-режим, сучасний JS (без зайвих поліфілів), розмір бандла і ледаче завантаження;
- lit-html: актуальні патерни, директиви, керування станом і перерендером;
- CSS: чи використано доречно `:has()`, вкладеність, container queries, `dvh`/`svh`, `color-mix()`,
  логічні властивості, `prefers-reduced-motion`, `prefers-color-scheme`; `<dialog>`/popover замість
  саморобних модалок; View Transitions — **лише** якщо дає користь. Перевіряй статус Baseline.
- PWA: маніфест, service worker, оновлення версії, офлайн-режим.
- Залежності: `npm outdated`, `npm audit`.

База — RLS-політики з `(select auth.uid())` (initplan), індекси під політики, `search_path`,
актуальність supabase-kt / supabase-js і способу автентифікації (PKCE тощо).

Наприкінці розділу — **висновок простою мовою** (5–8 речень): чи правда, що цей код «не сучасний»,
що з цього реально впливає на користувачів чи майбутню підтримку, а що — питання смаку.

### E. Архітектура й стан

1. ViewModel: назовні лише read-only `StateFlow`, незмінний UI-стан.
2. Одноразові події (снекбари, навігація) — чи не повторюються й не губляться.
3. Process death у формах: код сім'ї, оцінка, домашка, редактор розкладу, нове заняття, пароль.
4. Проковтнуті винятки або, навпаки, падіння на основному шляху.
5. Дублювання логіки між Android і сайтом (напр. правила занять у `core/domain/Clubs.kt` і `src/lib/clubs.ts`,
   і в SQL) — чи збігаються правила валідації в усіх трьох місцях.

### F. Продуктивність

1. Compose: нестабільні класи (Compose Compiler Metrics), щосекундні таймери, що перекомпоновують
   весь екран, алокації в `drawBehind`/`Canvas`, `key`/`contentType` у Lazy-списках.
2. Холодний старт Android, baseline profile — чи є і чи потрібен.
3. Віджет Glance: частота оновлень і батарея.
4. Сайт: розмір JS/CSS, LCP/INP/CLS (Lighthouse для мобільного), шрифти (font-display, підмножини).

### G. UI/UX — **не менш важливо, ніж безпека**

Дивись очима двох людей: **13-річного школяра** і **зайнятого батька**. Для кожного екрана Android
(у трьох стилях × світла/темна) і сайту (телефон і комп'ютер) зроби знімок і оціни:

1. **Головні сценарії від початку до кінця**, рахуючи кроки й місця, де легко заплутатися:
   реєстрація → створення сім'ї → запрошення дитини; дитина вступає за кодом; додати оцінку й
   побачити нарахування; додати домашку й позначити виконаною; заповнити розклад і дзвінки;
   **додати позашкільне заняття й увімкнути нагадування**; вибрати місце для тривог; видалити акаунт.
2. **Евристики Нільсена** (видимість стану, відповідність реальному світу, контроль і скасування,
   послідовність, запобігання помилкам, впізнавання замість запам'ятовування, гнучкість, мінімалізм,
   зрозумілі помилки, допомога) — для кожної порушеної: екран, знімок, що саме, як виправити.
3. **Стани**: порожні, завантаження, помилка мережі, офлайн, довгі назви, 12 уроків, 20 занять,
   тривога + синхронізація одночасно, канікули, вихідні, сім'я з кількома дітьми.
4. **Послідовність**: Android vs сайт (одні й ті самі слова, порядок, кольори), три стилі між собою,
   однакові відступи й кути карток, плаваючі панелі (`LocalChromePadding`) — чи ніде вміст не
   обрізається й не ховається під панелями (зокрема `AlertRegionScreen`, редактор розкладу, діалоги).
5. **Тексти українською**: зрозумілість для 13-річного, тон, помилки, однаковість термінів
   («заняття»/«гурток», «урок»/«предмет»), обрізання слів.
6. **Ігровий стиль**: чи мотивує (XP, рівні, серії), чи не тисне, чи не створює хибних стимулів
   навколо грошей; чи немає «темних патернів».
7. **Доступність**: контраст WCAG (порахуй для реальних кольорів з `Theme.kt`, включно з сірими
   підписами й вимкненими кнопками, в усіх стилях і темах), масштаб шрифту 1.3 і 2.0, TalkBack
   (`contentDescription`, `Role`, стан), зона дотику ≥ 48dp, клавіатура й фокус на сайті, axe.
8. **Рух і відгук**: ripple, haptic на значущих діях, анімації, повага до «вимкнути анімації».

Для кожної UX-знахідки: знімок, хто страждає (дитина / батько / обидва), наскільки часто трапляється,
пропозиція (1–3 речення, за потреби — простий ескіз словами).

### H. Збірка, CI, тести

1. Release: R8, `debuggable`, логування, підпис, перевірка ViewModel у dex (див. `HiltConventionPlugin`).
2. CI (`.github/workflows`): що перевіряється, чого бракує (напр. e2e сайту, перевірка міграцій).
3. Тести: що покрито, які критичні шляхи без тестів (синхронізація, ролі, винагороди, заняття, нагадування).

## Формат результату

Звіт — `docs/audit-YYYY-MM-DD.md`:

1. **Підсумок для власника** (≤ 12 рядків, без жаргону): загальна оцінка, 3–5 головних ризиків,
   відповідь на питання «чи сучасний код».
2. **Таблиця знахідок**: `ID | Серйозність | Розділ | Коротко | Доказ | Упевненість | Зусилля (S/M/L)`.
   - **Критично** — витік/зміна чужих даних, ескалація прав дитини, втрата даних, падіння на основному шляху;
   - **Важливо** — помітна помилка поведінки чи UX, порушення доступності, ризик для Play, deprecated із дедлайном;
   - **Бажано** — якість коду, «кращий спосіб», полірування.
3. **Детально** по кожній: що не так → доказ (код / знімок / джерело) → як відтворити → як виправити → зусилля.
4. **Сучасність коду** — таблиця з розділу D і висновок простою мовою.
5. **UX** — знахідки з розділу G, згруповані за сценаріями, зі знімками.
6. **Що зроблено добре** — коротко, з доказами (щоб не зламати під час виправлень).
7. **Неперевірене й гіпотези** — з причиною.
8. **Порядок виправлень**: спершу A і C, далі важливі UX-проблеми, потім решта — пакетами,
   які можна робити окремими PR.

Після звіту — коротке повідомлення в чат: кількість знахідок за серйозністю, три головні висновки,
шлях до файлу. **Нічого не виправляй**, поки власник не вибере, що робити.
